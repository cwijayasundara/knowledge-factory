A knowledge factory for root-cause analysis

Flags, a curator, a reviewed bundle and an eval gate, built around AutoRCA and measured against a sealed baseline.

Abstract. AutoRCA is an agent that finds the root cause of an alert over an ontology-backed knowledge graph. Its operating knowledge lives in prompt text, and what it learns in a run is thrown away. This paper describes a knowledge factory built around it, following Harrison Chase's pattern: working agents flag the knowledge they lacked, one curator turns flags into proposed changes to a versioned bundle, an eval gate and a person decide the merge, and a measurement asks whether the curated bundle makes the agent better. The factory is a separate system that knows nothing about observability; AutoRCA connects to it through five small patches. The loop has run end to end: nine flags became three clusters and seven curator-written files, with the judge model catching two unsupported claims on the way. The headline measurement has not been run, and on the held-out seeds the starved baseline already scores 63 of 63 on top-1, so the measurement as specified cannot show a gain. Section 13 lists what is and is not established.

1Context

AutoRCA, built earlier and described in the companion white paper, is a DeepAgents commander with seven specialists (topology, change, metrics, logs, traces, alerts and incidents, history). It works over a read-only, as-of RDF store and runs on GLM through Fireworks. It is evaluated on seven scenarios against a held-out answer key: top-1, top-3, a trap in the hero scenario, a control scenario with no fault where the right answer is to abstain, and evidence precision.

This paper takes that agent as given. Section 2 summarises it from the e2ekg repository, so every statement about AutoRCA traces to code or a stored run. The companion paper is the full account of the ontology and the correlation engine.

The new element is a loop around the agent. It follows How to build a knowledge factory (Harrison Chase, 21 November 2026), which describes the pattern and ships no code. The repository is a working version of it, with a governance model and a measurement that the article leaves open.

2AutoRCA, the working agent

This section summarises AutoRCA from the e2ekg repository (docs/ARCHITECTURE.md, docs/EXPERIMENTS-needle-in-haystack.md and the code), so each statement can be traced to code or a stored run. e2ekg rebuilds the system described in Netflix's post on ontology-driven observability: messy telemetry goes in, a knowledge graph is built from it, and an agent finds the one true root cause among red herrings.

The world it works in

One typed, frozen Scenario model is the single source of truth. A generator renders it into metrics, events, logs, traces, Slack and a service catalog, with registered mess injectors for everything real telemetry does: one application under seven names, tag-key drift, mixed units and time zones, per-host clock skew, head-sampled traces with orphan spans, and chat with nicknames and retractions. Every injection is recorded in a manifest. The same seed gives a byte-identical raw tree. The answer key is written outside the raw tree and only the scorer reads it.

From raw bytes to a graph

Preprocessing follows a five-step entropy ladder, with a conservation ledger that fails the ingest if anything is lost.

StepWhat it doesContract
L1 parseSplits every raw file into record spans; each gets a stable id source|path|offset|length|sha256Every byte lands in exactly one span; failures go to quarantine with a reason
L2 normalizeUTC times, units, per-host clock-skew correction from trace pairsOriginals are kept next to normalized values
L3 identitySurface names to catalog URIs: exact, then fuzzy, then an LLM choosing from the catalog onlyAn unresolved name stays a literal and never becomes an application
L4 fingerprintLog templates, anomaly change points, trace edge statisticsRaw telemetry never enters the graph; each pattern carries a selector back to its rows
L5 interpretChat into typed claims, by an LLM whose output enums are the SKOS schemesFailures become quarantine rows; no message is dropped

The harvest then runs ten enrichers in order (catalog, topology, changes, metrics, logs, traces, alerts and incidents, chat, history, correlation). Each writes its own named graph in an embedded Oxigraph store, is idempotent, and is best effort: a failing enricher clears its graph and never blocks the rest. SHACL validates the union. Every derived fact carries ops:rawSelector or prov:wasDerivedFrom, so any claim in a report can be drilled back to raw bytes.

The ontology is code: an OWL core with five families (identity, change, signal, response, reasoning), eight closed SKOS schemes that double as LLM output contracts, SHACL shapes, and 15 competency questions that run in the test suite. There is no generic Service type; the only software identity is ops:Application, gated by the catalog. Extensions are proposed by an LLM and pass an additive-only guard, SHACL and the full question suite before a person moves the file in. Four have been approved.

The agent sees an as-of store, built from only what was observable at the alert plus 30 minutes. Log templates are re-mined from the pre-cutoff lines, so a later line cannot reshape what the agent saw.

The correlation engine

A deterministic beam search turns 13 signal types into causal chains. An edge from a to b needs time order within a ten-minute window, a plausible role pair, and a topology gate: b must be on a's application or on one that transitively calls it. A change is also vetoed if the cascade it would explain had already started. Pair scores multiply a prior for the signal pair (for example 0.95 for config change to autoscaling) by temporal proximity and severity. A chain's confidence is the geometric mean of its pairs, and chains below 0.6 are dropped. The engine proposes chains with their evidence and never concludes. Without the topology gate it scores 2 of 7 on top-1.

The agent

AutoRCA is a DeepAgents commander with seven specialists, on GLM-5.3-flash through Fireworks. The harness removes the shell and the general-purpose subagent, so a specialist sees only its own slice of the world.

The commander finds the symptom, treats the incident's filed application as a hypothesis, dispatches all seven specialists in one turn, reads their findings grouped by application, proposes every candidate, gathers facts per candidate (reach, timing, call-path status, what was already happening, coverage of the cascade), and weighs them. Each rejected candidate needs a stated refuting fact. Two survivors lower the confidence, and none means inconclusive. The answer is a pydantic RCAReport whose hypotheses must cite graph URIs.

Fourteen typed tools stand between the model and the graph, because a flash-tier model writes poor SPARQL against an unfamiliar ontology. Results are capped near 4,000 characters, errors say what to change instead of raising, and nicknames resolve through the same L3 resolver. candidate_evidence returns facts only and decides nothing, and an ablation arm runs the agent without it. A fast path runs the same tools and schema with a deterministic prefetch and one-shot specialists: on the hero alert it cut 43 model calls to 8, input tokens from 410K to 33K, and wall time from about 32 s to 17 to 20 s, and it escalates to the full path when the answer is weak.

Evaluation

e2ekg eval scores three LLM arms (graph, graph_no_evidence_tool, raw_only, which reads the as-of raw files with no graph) and three engine arms (engine_top, engine_no_topology, engine_no_explain_away). Metrics are top-1, top-3, evidence precision (the share of cited evidence that reaches the answer key's evidence), a trap count for choosing a planted red herring, and control false positives. The factory adds one arm, graph_kb, which is graph plus the factory tools.

At normal density raw_only also reached 100% top-1, so the benchmark could not show the graph's value on accuracy alone. The authors' own experiment notes close that gap with a density sweep. Background traffic grows eight times, the as-of graph stays within about 5% of the same size, and the graph arm stays flat.

Two further experiments in the same notes are null results. Replacing the incident's deliberately wrong filed application with none left top-1 at 21 of 21, and live GLM chat labels in place of scripted ones also scored 21 of 21. The notes list their own limits: one world, one seed, seven fault scenarios, and a needle planted by the same hand that grades the search.

Where the factory attaches

The graph keeps data and the factory keeps knowledge about it, as the article advises. AutoRCA's knowledge today is the prompts in agent/prompts/, the catalog hints and the graph. The factory leaves the ontology path alone and covers the rest: the bundle holds data-access guidance such as "trace service names are aliases, not catalog ids", and a flag from AutoRCA names what it could not find. e2ekg's own flywheel is the nearest prior art: a chain becomes a prior only when it is top-1 correct and a person approved it, which is the same human-in-the-loop rule the factory applies to knowledge.

3The idea and the problem it answers

The article's claim is that the missing ingredient for enterprise agents is neither a better model nor more context, but better knowledge: how the company works, which source to trust, where data lives and how it is accessed. Context is what an agent has in hand during a task. Knowledge is the reusable understanding that has to be maintained so the context is right. Data a company already stores reliably stays where it is; the factory holds the knowledge about it.

The pattern has three parts, and this build maps one to one onto them:

ArticleThis build
Working agents flag missing or wrong knowledge with a toolkf_flag on AutoRCA's commander and specialists. The handler, not the model, attaches agent, run id, scenario and time.
A curator agent runs on a cadence over raw sources, traces and flagskf curate: a DeepAgents agent on GLM with an eight-stage flow. One command per run; not yet scheduled.
A knowledge store of skills, domain knowledge and data-access guidance, in an open formatbundle/: OKF v0.3 concepts plus plain SKILL.md skills, in git, one branch per curator run.

For AutoRCA the problem is concrete. Its knowledge is prompt text that an engineer edits by hand, with no source and no review tier, and the findings of a run are discarded when it ends. Figure 5 shows what changes.

4Architecture

The repository is the article's factory, built as a separate system, with AutoRCA as its first user. Nothing in the factory core knows about observability. Everything specific to e2ekg sits behind the patches in section 12. Figure 6 is the whole system; the legend below is used by every figure in this paper.

working agentflags: untrusted dataknowledgecuration and governancerefusede2ekg data pipeline

Three properties follow from the picture.

  • The agent cannot write knowledge. It has one write path, to the flag queue, and two read tools over a frozen snapshot of main. A merge during an eval run never reaches that run.
  • The curator cannot merge. It can only propose a branch. Merging is a separate command that checks CI, the tier, the gate and an approval.
  • The answer key is not reachable from either side. The curator reads an as-of raw view built by kf raw-view; no permission list names the answer-key directory except to deny it.

Goals, and what would count as failure

The design spec states four anti-goals. Each is something that would make the build a failure even if it ran:

  1. The curator or the agent ever reads the held-out answer key.
  2. A working agent writes knowledge directly.
  3. A gain that comes from tuning prompts to the test scenarios rather than from curated knowledge.
  4. Knowledge stored in two places, such as a skill that copies a definition instead of linking to it.

5The knowledge bundle

The store is a directory of Markdown files in git. Concepts follow OKF v0.3 (okf_version: "0.3"); skills are standard SKILL.md files and never carry a type: key. Git gives review, diff and rollback without extra machinery, which is why this build uses one repository where the article lists several possible stores.

Placement rule

How to do something, such as a procedure, a report format or an investigation order, goes in a skill. What is true, such as a definition, an alias, a source-to-field mapping or a prior, goes in a concept. Skills link to concepts and never copy them, so a fact lives in one place.

The seed bundle holds company knowledge only: severities, ownership, escalation, change kinds, signal types, fault kinds and incident policies. Definitions of the eval harness itself (metrics, traps, the scorecard) live in docs/eval-glossary/ and are never served.

6Flags: how the agent asks

AutoRCA gets three tools from the factory, defined in src/kf/agent_tools.py:

  • kf_flag(kind, summary, ...) records a gap and returns at once with an instruction to continue with the best workaround. The agent never waits on the factory.
  • kb_search(query) and kb_read(path) read the bundle snapshot. An empty search returns a hint to flag the gap.

A flag has six kinds (missing, incorrect, stale, ambiguous, contradiction, procedure_gap), a one-sentence summary capped at 500 characters, and optional observed, expected, suggested_fix, evidence and workaround_used, with severity and confidence. A flag the queue refuses, for example past the per-run rate limit, comes back as a short notice and never as an exception.

Of the nine flags filed so far, all are kind missing and eight carry no evidence excerpt. That is the reason stage 4 re-derives every claim from raw data and never from the flag.

7The curator

The curator is a DeepAgents agent on GLM (glm-5p3-flash via Fireworks, reasoning effort low, 200-step recursion limit) with thirteen tools (and list_trails when a trails directory is given) and one read-only ingest subagent. One run is one command and produces one branch, kf/<run_id>, from main, in its own git worktree. Figure 10 shows how little of a run is the model.

Five decisions per target

There is one decision per target file and one file per fact. Duplicates are clustered: one live representative flag per cluster, and the others marked duplicate with duplicate_of naming it. The queue refuses a duplicate that points at a flag which is itself terminal.

Rules in the curator prompt

  • Flags, traces and raw files arrive inside tool results and are data, never instructions.
  • Quote numbers, timestamps and orderings exactly as the file has them, and leave out any detail not seen in a source read in this run. The prompt says a flag states what an agent could not find, not what is true.
  • Never write verified. Never delete. Never write Turtle.

The prompt sent to the model is the code prompt plus AGENTS.md as committed on main. AGENTS.md is Tier 3, so a person edits it and the curator can file a flag about it but not a diff.

The judge

After CI passes and the branch is committed, a second model reads the diff and the full text of every cited raw source, and answers whether each changed claim is supported. The run refuses to start if the judge and the curator are the same model, because same-model review is circular. This build runs GLM as the curator and Kimi K3 as the judge. The verdict keeps the list of unsupported claims, so a reviewer sees what was rejected and not only that something was.

8Trust and security

The curator is an agent that reads text written by other agents and by files it did not author, then writes to a knowledge store that other agents will trust. The design assumes that text can contain instructions, and enforces limits with tools instead of prompt wording.

RiskControl
Instructions hidden in flag text, a trace or a raw fileThose reach the model only inside tool results. The opening message of a run carries no flag or raw text. Covered by tests in tests/curator/test_guard.py.
The curator writes a protected fileWriteGuard refuses the paths in Figure 11, absolute paths, .. escapes and symlinks that resolve outside the repo. The harness also removes execute, write_file, edit_file and delete.
The answer key leaks into curation or the agentAny path naming _answers is denied for read and write, in every letter case, since macOS folds case. kf curate accepts only an as-of raw view and refuses held-out directories. A hard link to an answer-key file would defeat a path check, so the raw directory must not contain hard links; AGENTS.md records this as a rule.
A fabricated or unsupported claim reaches the bundleEach new claim cites a raw id read in the same run or the decision is ESCALATE. A judge that is a different model checks the cited text.
The curator approves itselfIt never writes verified. The stamp is added by kf review approve, with the approver's name from the command line, never from git config.
A crash leaves half a changeA run record still marked running means a crash. The next run deletes that branch and worktree and takes the flags back.

9Review and merge

Review is tiered by what a change asserts, not by how big it is. The classifier looks at each changed file and the highest tier wins.

TierTypical changeNeeds
0Index and log regeneration, link repair, mechanical stampsCI, then kf review auto-merge. Bundle files only; never an approval line.
1New concept with a cited raw source; a skill; a data-access conceptOne person, and a passing eval gate
2Changing a definition or prior; deprecation; low confidence; no sources; touching reviewed contentA person, a second distinct person or judge_ok, and a passing gate
3kf-profile.yaml, AGENTS.md, CODEOWNERS, computations/, tier rules, the curator promptHumans only. A curator branch carrying Tier 3 is refused.

The approver may not be the removal-list author, and a scripted approver is accepted only on runs marked as tests. Both are recorded on every approval and checked again when G2 is computed.

10Measurement design

The article offers no metric. The question here is whether curated knowledge makes AutoRCA better, and there is an obstacle: AutoRCA already scores close to the maximum on its own scenarios, so a curator has nothing to improve. The design starves the agent first.

Starve, seal, split

  • Starve. A removal list names exact text to delete from e2ekg prompt files, for every LLM arm alike, through patch 0003. Only knowledge that can be derived from the raw data may be listed, with a note on where it can be derived from, so the curator is never asked for something it cannot know.
  • Seal. The list is written outside the repo (~/.kf/removal.yaml) and committed only as a sha256, an author and a time. The seal commit must predate the first measured run. Each starved run copies the list into a private directory, and G2 checks that the copy still matches the seal. The list is opened only after the G2 report is written. kf seal refuses a list that is empty, inside the repo, or whose text appears in a bundle file.
  • Split. Seeds 11, 12 and 13 feed the curator and the gate. Seeds 21, 22 and 23 score G2 and nothing else. Choosing merges by held-out scores would be selection on the test set, so the gate uses curation seeds only.

Eval gate

kf eval gate runs graph_kb starved on the curation seeds twice, over main and over the branch with its proposed concepts served as if approved, in a snapshot copy only. Six evaluations run in parallel and take about five minutes. A branch fails if top-1 drops by more than one scenario-run, or if the trap count or control false positives rise. The scores and their provenance are written into the run record, and kf review approve refuses stale gate scores.

G2 verdict

kf eval g2 compares the three arms and returns one of three results: pass, fail, or invalid. It is invalid, and writes no report, if the three run sets are not comparable (data roots, scenarios, runs, one e2ekg commit, one --now), if the seal is missing or broken, if any approval is scripted, a test run or by the list author, if the runs are not held-out, or if any bundle/ change between kf-seed and the measured commit did not arrive through a kf review merge of a kf/<run_id> branch, with a run record, an approval line and a kf-curator author. A direct commit or a hand merge fails closed, and the reason names the commit and file.

11Results to date

From flags to files

Nine flags came from two curation seeds (seeds 11 and 12) of graph_kb runs with the starve switch on. In run curate-20261123T0540Z they became three clusters. Five flags were duplicates of a live flag. One was held. Three were live and moved to in_review.

The cluster for flags 2, 5 and 7 shows what the factory does that a prompt edit does not. The agent reported that no trace edges existed in the window. The curator found OTLP span exports in the raw data and wrote that edges are not precomputed but can be rebuilt by joining each span to its parent through parentSpanId. In the earlier run it also wrote a skill, localize-degraded-call-path, which warns that trace service names are catalog aliases such as artwork for artwork-svc, and that matching ids verbatim returns empty results that look like missing telemetry. Both are the curator's reading of the raw data, still proposed and not yet verified by a person.

The judge earned its place

On run 6 the first judge verdict was false with two unsupported claims. The curator had written that span exports exist under traces/zipkin/, but the only source it cited was the OTLP file. It had also described a session-svc span as a child of the edge-gateway span, where in the source it is the child of the search-svc span. Both were fixed by hand in three commits and the branch was re-judged as supported. The run record keeps the original verdict beside the new one.

The gate and the baseline

The gate passed on both curator branches: 21 of 21 top-1 on main and 21 of 21 on the branch, no traps, no control false positives. The README is explicit that this is a no-regression check only, because the curation seeds already score at the ceiling. The held-out starved baseline scored 21 of 21 on each of seeds 21, 22 and 23, with 0 of 3 hero traps and 0 of 3 control false positives.

What this means for G2

G2 requires the curated arm to beat the starved arm by at least two top-1 scenario-runs. The starved arm already has the maximum, so the condition cannot be met on these seeds, whatever the curator does. Whatever the sealed removal list took out (it was not opened for this paper), it did not lower top-1. Evidence precision, at 43, 35 and 33 percent on the baseline, is where headroom remains.

The ontology boundary

e2ekg already has its own curator for the ontology: it mines gaps, an LLM proposes Turtle, an additive-only gate with competency questions and SHACL checks it, and a person moves the file. The factory leaves that path alone. When a flag implies a missing ontology concept, such as an uncovered error template, the curator decides ESCALATE and files a structured need (error_template, metric_tag or event_type) that kf ontology-needs turns into the exact e2ekg ontology propose command. Ontology proposals are frozen during a measurement so the bundle is the only variable.

13Limits and status

Established

The machinery runs end to end and is governed: flags to curator to judge to gate to a branch, with a write guard, tiers, a sealed baseline and a split between curation and held-out seeds. The tests cover the guard, the queue, the tiers, review, the gate and G2 (305 test functions, run with a scripted model and no LLM cost).

Not established

That curated knowledge makes AutoRCA better. G2 has not been run, and as section 11 shows it cannot show a top-1 gain on these seeds.

Known gaps

  1. The curated files are on main without going through review. The two curator branches were merged with plain git merge, not kf review approve. The seven files still say x-kf-review: proposed and carry no verified stamp, no approval line exists, and their flags remain in_review. So kb_search does not serve them to the agent, and G2 would refuse them as a hand merge. The first of the two branches had a judge verdict of false when it was merged.
  2. Headroom. Top-1 is at its ceiling in the starved baseline. Making G2 meaningful means a harder removal list, harder scenarios, or a scored metric with room to move such as evidence precision. A new list needs a new seal and a new baseline.
  3. Small sample. Nine flags from two seeds, one curator model, one judge model. A judge is itself a model and can miss an error.
  4. Run record and decisions. A record can list decisions for targets never written. Run 6 lists six decisions and wrote three files; one of the unwritten six is a test probe that stayed in the record.
  5. Evaluation setup. Chat claims in the eval come from a scripted stand-in, not live GLM extraction.
  6. One workflow, one reviewer role. The seal records its author as claude, and G2 needs the approving person to be someone else. Review runs on local branches and a CLI in place of pull requests; the tier rules and CI would be the same on GitHub.
  7. AutoRCA's own evidence is narrow. One world, one seed and seven fault scenarios, with a needle planted by the same hand that grades the search. The density sweep uses one run per cell at 4× and 8×.
  8. Not scheduled. A run is one command. A cron or a hosted schedule around the same command is the missing piece.

Next steps

  • Decide how to give G2 headroom, then re-seal and re-baseline.
  • Collect flags at larger scale and report the curator metrics the code already computes: declined and held share, recurrence, review acceptance, citation coverage, stale and orphan ratios.
  • Schedule the curator, and point a second agent at the same bundle.
